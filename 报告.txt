一、自主模式行为机制（核心问题）
现状分析
自主模式由cmd/companion/agent/下的多文件协作实现：

autonomous.go                ← 外层设计者Loop注册（update_plan + delegate_task）
autonomous_controller.go     ← 编辑距离计算（任务去重）
loop.go                      ← TAOR核心循环
plan.go + plan_manager.go    ← 计划管理（update_plan工具 + 持久化）
task_manager.go              ← 任务管理（create/update/list）
orchestration.go             ← 编排引擎（多loop协调）
delegate.go                  ← 任务委托
subagent.go                  ← 子Agent管理
exec_state.go                ← 执行状态持久化
session_manager.go           ← 会话管理
progress_checker.go          ← 进度检查
reviewer.go                  ← AI审核
storm_breaker.go             ← 风暴断路器
circling.go                  ← 绕圈检测
compress.go                  ← 上下文压缩
snapshot.go                  ← 文件快照
message_store.go             ← 消息持久化
evalstore.go                 ← 评分存储
核心问题
1.1 计划-任务-执行状态三者关系模糊

plan_manager.go 管理计划(PlanRec)，有步骤(steps)和状态
task_manager.go 管理任务(Task)，有依赖和状态
exec_state.go 管理执行状态(ExecutionState)，有步骤记录
三者本质描述同一件事的不同维度，但数据结构和存储互相独立，没有统一的关联机制
缺少状态机：执行过程中 plan→step→task 的流转靠update_plan工具手动推进，没有自动状态跃迁
1.2 前端展示与后端状态不同步

update_plan工具返回纯文本给LLM，通过事件通道的Args传给前端
前端agent-events.js的onPlanUpdate回调从事件中提取plan数据
没有全量plan拉取API，页面刷新后plan状态丢失
前端没有Plan的独立视图，只是聊天消息中的一部分
1.3 连续性/回溯性不足

Loop完成后消息写入JSONL，但OnBatchPersist每轮都写全部消息（diff去重）
没有对话级别的「检查点」概念，无法精确跳转到某个执行阶段
compress.go的上下文压缩会丢弃中间消息，丢失回溯粒度的细节
1.4 记忆化与知识库更新脱节

memory.go 的记忆存储在工作区.pair/memory/下，每条一个.md
记忆召回靠关键词/CJK二元组重叠打分（taskTokens），无向量语义检索
知识库(projectinfo.go)是给用户看的中文文档，与记忆分离
任务完成时没有自动触发记忆写入或知识库更新
重构方向
问题	方案
三者关系模糊	统一为「执行计划」模型：Plan包含Task列表，Task包含Step列表，执行状态是Plan的运行时视图
前端不同步	Plan作为一等公民：提供REST API（GET /api/plans/:id）、独立前端组件、WS推送plan更新
连续性不足	引入「检查点」机制：每N轮或关键节点记录检查点，支持分支/回退
记忆化脱节	任务完成后自动调用memory_write + 知识库更新工具
二、代码LSP两套机制冗余（已确认）
现状
项目中存在 三套代码分析机制：

机制	位置	功能	状态
internal/lsp/	internal/lsp/client.go + manager.go + lsptools.go	完整LSP客户端：Manager管理多语言server、诊断、定义、引用、hover	已实现但未接线（registerLSPTools未在registerDefaultTools中调用）
filesymbol.go 内嵌LSP	cmd/companion/agent/filesymbol.go	嵌入式LSP（自建JSON-RPC连接gopls等），提供get_file_symbols、find_symbol_usages	当前实际在用
cmd/companion/langsrv/	cmd/companion/langsrv/langsrv.go	编辑器UI的LSP服务器注册表（30+语言配置）	编辑器专用
冗余分析
filesymbol.go（约700行）自己定义了全套LSP类型：

type lspPosition struct { Line, Character int }
type lspRange struct { Start, End lspPosition }
type lspLocation struct { URI string; Range lspRange }
type lspDocumentSymbol struct { ... }
type lspServerDef struct { cmd, args, langID string }
而internal/lsp/已经有了更完善的实现（含跳转定义、引用查找、hover、诊断、位置编码UTF8/UTF16支持、诊断版本管理、文档同步等）。

结论：filesymbol.go的嵌入式LSP实现与internal/lsp/完全重复，前者应废弃，统一迁移到internal/lsp/。

重构方案
将filesymbol.go中get_file_symbols、find_symbol_usages、check_impact、find_circular_deps迁移到internal/lsp/
internal/lsp/补全textDocument/documentSymbol和textDocument/references能力（目前已有definition/hover/diagnostics）
在tools.go:registerDefaultTools中启用registerLSPTools
删除filesymbol.go中的冗余LSP实现（约400行）
保留cmd/companion/langsrv/ 作为编辑器专用配置（职责不同，不冗余）
三、存储数据库化（核心架构问题）
现状 — 所有JSON/JSONL/MD存储一览
.pair/conversations/{id}.jsonl              ← JSONL 行追加（对话消息）
.pair/conversations/{id}.summaries.json     ← JSON 数组（压缩摘要）
.pair/conversations/index.json              ← JSON 数组（会话元数据）

.pair/plans/{id}.json                        ← JSON 独立文件（计划）
.pair/plans/_bindings.json                   ← JSON（线程绑定）

.pair/tasks/{id}.json                        ← JSON 独立文件（任务）
.pair/tasks/execution-states/{id}.json       ← JSON（执行状态）

.pair/memory/{name}.md                       ← Markdown（记忆）
.pair/memory_index.json                      ← JSON（记忆索引）

.pair/project-info/**/*.md                   ← Markdown（知识库）

.pair/codegraph/graph.json                   ← 大JSON（代码图谱 → 可能数十MB）
.pair/codegraph/index.json                   ← JSON（图谱索引）

.pair/snapshots/{relPath}/{timestamp}        ← 文件快照
.Pair/evals/records.json                     ← JSON数组（注意大小写差异）
.pair/assets/{scope}/{type}/{id}.json        ← JSON（资产）
已确认的问题
问题	影响	严重度
JSONL无上限增长	长期对话的文件→数百MB，每次readJSONL全量读入内存	⚠️ 高
codegraph/graph.json全量快照	大项目（1000+文件）图谱文件可达50-200MB，序列化/反序列化开销巨大	⚠️ 高
JSON全量覆盖	改一条任务也重写整个JSON文件，无事务保障	⚡ 中
snapshot目录膨胀	每文件20份快照 × 修改文件数 = 大量小文件	⚡ 中
大小写不一致	.Pair/evals/ vs .pair/（跨平台隐患）	⚡ 低
无事务/无原子性	多文件间一致性无保障（crash后可能不一致）	⚠️ 高
索引性能差	对话列表加载整个index.json；记忆搜索纯关键词扫描	⚠️ 高
没有查询能力	无法「查昨天所有失败任务」，只能遍历所有JSON文件	⚠️ 中
重构方案：统一数据库化
建议采用 SQLite（嵌入式、零配置、Go标准库modernc.org/sqlite或github.com/mattn/go-sqlite3）：

.pair/pair.db  ← 单一 SQLite 数据库文件
数据表设计：

-- 对话
CREATE TABLE conversations (
    id TEXT PRIMARY KEY,
    title TEXT,
    workspace_root TEXT,
    created_at TEXT,
    updated_at TEXT,
    summary TEXT,
    msg_count INTEGER DEFAULT 0
);

-- 消息（替代 JSONL）
CREATE TABLE messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    conv_id TEXT NOT NULL REFERENCES conversations(id),
    idx INTEGER NOT NULL,          -- 顺序号
    role TEXT NOT NULL,            -- system/user/assistant/tool
    content TEXT,
    tool_calls TEXT,               -- JSON
    tool_call_id TEXT,
    name TEXT,
    reasoning TEXT,
    segments TEXT,                 -- JSON
    created_at TEXT,
    UNIQUE(conv_id, idx)
);
CREATE INDEX idx_messages_conv ON messages(conv_id, idx);

-- 计划
CREATE TABLE plans (
    id TEXT PRIMARY KEY,
    conv_id TEXT REFERENCES conversations(id),
    status TEXT DEFAULT 'active',
    task TEXT,
    reasoning TEXT,
    created_at TEXT,
    updated_at TEXT
);

-- 计划步骤
CREATE TABLE plan_steps (
    id TEXT PRIMARY KEY,
    plan_id TEXT NOT NULL REFERENCES plans(id),
    description TEXT,
    status TEXT DEFAULT 'pending',
    dependencies TEXT,              -- JSON数组
    sub_task_ids TEXT,              -- JSON数组
    sort_order INTEGER
);

-- 任务
CREATE TABLE tasks (
    id TEXT PRIMARY KEY,
    subject TEXT,
    description TEXT,
    status TEXT DEFAULT 'pending',
    dependencies TEXT,
    conv_id TEXT REFERENCES conversations(id),
    plan_id TEXT REFERENCES plans(id),
    created_at TEXT,
    updated_at TEXT
);

-- 记忆（带FTS全文检索）
CREATE TABLE memories (
    name TEXT PRIMARY KEY,
    type TEXT,
    description TEXT,
    body TEXT,
    created_at TEXT,
    updated_at TEXT
);
CREATE VIRTUAL TABLE memories_fts USING fts5(name, body, content=memories);

-- 知识库
CREATE TABLE project_info (
    path TEXT PRIMARY KEY,
    title TEXT,
    level TEXT,              -- overview/module/detail
    body TEXT,
    updated_at TEXT
);

-- 代码图谱（分实体+关系，不再一个JSON）
CREATE TABLE code_entities (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    kind TEXT NOT NULL,       -- function/struct/interface/...
    name TEXT NOT NULL,
    file_path TEXT,
    line INTEGER,
    signature TEXT,
    package_name TEXT,
    module TEXT,
    UNIQUE(kind, name, file_path, line)
);
CREATE INDEX idx_entities_name ON code_entities(name);
CREATE INDEX idx_entities_file ON code_entities(file_path);

CREATE TABLE code_relations (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source_id INTEGER NOT NULL REFERENCES code_entities(id),
    target_id INTEGER NOT NULL REFERENCES code_entities(id),
    kind TEXT NOT NULL,       -- calls/imports/contains/...
    UNIQUE(source_id, target_id, kind)
);

-- 评分记录
CREATE TABLE evals (
    id TEXT PRIMARY KEY,
    task TEXT,
    agent_model TEXT,
    judge_model TEXT,
    scores TEXT,              -- JSON
    total INTEGER,
    strengths TEXT,
    weaknesses TEXT,
    feedback TEXT,
    tool_calls INTEGER,
    tool_errors INTEGER,
    created_at TEXT
);

-- 快照（元数据管理，文件仍存磁盘，但引入TTL自动清理）
CREATE TABLE snapshots (
    file_path TEXT,
    snapshot_id TEXT,
    created_at TEXT,
    PRIMARY KEY(file_path, snapshot_id)
);
迁移策略
渐进式，不一次性大爆炸：

Phase A — 新增SQLite数据库层（.pair/pair.db），与现有JSON写并存
Phase B — 消息存储迁移：新消息写SQLite，旧JSONL只读兼容
Phase C — 代码图谱迁移：实体/关系写入SQLite表，删除graph.json
Phase D — 记忆/知识库迁移：Markdown→SQLite + FTS5全文索引
Phase E — 计划/任务/评分迁移，关闭JSON后端
