## 一、背景与本次调整

### 1.1 现状问题（同 v1）

| 项 | 现状 | 问题 |
|---|---|---|
| 访问控制 | Web 监听 `0.0.0.0:<port>`，局域网可达 | **无任何认证**——局域网内任何人获得完整控制权 |
| 用户体系 | 无登录/令牌/中间件；settings 无 user 概念 | 无法区分使用者 |
| 隔离粒度 | 已有「工作区/会话」级隔离（08-23 改造） | 无「用户」级隔离；"当前工作区"等为全局单例 |
| 微信桥 | 多账号（accounts.json），平台单主使用 | 无法分配用户 |

### 1.2 本次调整：两步走 + 插件化动态调度

用户决策（2026-09-17）：

> **两步走**：1. 总体架构主体改造；2. 认证及中间件、前端页走插件；架构支持插件中的**配置动态组合、增删的实时调度处理**。生产一旦运行就**只改参数运行、插件的动态加载或卸载**。

**解读**：
- **第一步 · 主体改造**（完成后**冻结**）：身份/隔离/权限主干 + 让插件能介入核心流程的"**运行地基**"（请求管线、身份传播、页面挂载点）。
- **第二步 · 插件化交付**：认证、中间件、前端页以插件形态交付；补齐"**调度能力**"（热装载/卸载/替换、参数热更、组合装配、管理界面）。
- **生产形态**：平台 = 稳定主体 + 可变插件；运行时只做两件事——**改参数**（会话时长/限速阈值/角色→工具集映射/各插件配置……）、**插件加载/卸载/替换**（换登录页/停限速/加审计……）。不编译、不重启。

### 1.3 可复用资产（已核查）

1. **工作区隔离路由模式**（08-23）：SessionManager 按 root 缓存 store/DB、ctx 三级根解析、`taskRuntimeRoot`、`cgEntries` 按 normRoot 键控——"按 key 路由多实例"范式可扩用户维度。
2. **工具集系统**（09-04/06）：全局通用集合（`.pair/toolsets/*.json`）按会话选择；内置 6 预设（计划讨论/全栈开发/办公/调试/基础/全功能）。
3. **插件体系**（见第四章盘点）：磁盘插件包、插件路由（先于宿主 mux 拦截）、设置项 schema、跨插件服务 provide/get、生命周期 run/stop/undefine、UI 槽位。
4. **统一拦截点**：`ExtRouteMiddleware`（ext_routes.go:142，"命中即执行、未命中放行"）——请求管线地基的天然挂点。
5. **内核路由表**：kernel_api.go 注册全部内置 API（key/method/path/desc），经 `RegisterExtRoute` 进同一路由表层。
6. **微信桥**：accounts.json 多账号，桥经 `POST /api/chat/send`（HTTP 同进程）投递。
7. **办公工具**：`tool-office` 磁盘插件（csv/word/xlsx/pdf/md 等）。
8. **隔离测试**：`workspace_isolation_test.go`（311 行行为规范）可扩展多用户用例。


**"参数"示例**：会话时长、免登录路径白名单、登录限速阈值、用户空间根、角色→工具集映射、各插件配置（审计范围、维护模式开关……）。

## 四、插件化设计（核心章节）

### 4.1 插件体系现状盘点

**已具备（直接复用）**：

| 能力 | 现状（证据） |
|---|---|
| 磁盘插件包 | `.pair/plugins/<id>/`：package.json + index.js（host 半）+ client.js（client 半），启动自动装载 |
| 插件 HTTP 路由 | `ctx.webServer.register`（exact/prefix + Node 风格 handler）→ `RegisterExtRoute`（jsplugin.go:865）；**先于宿主 mux 拦截，命中即执行、未命中放行**（ext_routes.go:141） |
| 内核接口挂载 | `ctx.kernel.install([{key}])`（core-api 插件模式） |
| 设置项 schema | `ctx.registerSettings`（text/number/boolean/select + default/hint/options），`getSettings/setSettings` 持久化——**"改参数"的载体现成** |
| 插件组合 | 跨插件服务 `provide/get`（含函数）+ `inject` 等待（依赖出现自动激活） |
| 生命周期 | `cordis(op=run/stop/undefine)` + 版本链 + 状态诊断（stopped/running/waiting/rejected/failed） |
| UI 槽位 | 壳 + 7 大区域槽位（single 替换型/list 叠加型）；client 半自动 global |
| 动态插件 | `cordis(op=define)` 内存定义 + `cordis.patch.json` 持久化 |
| 管理 API | `/api/plugins`（list/detail/action[start/stop/undefine]/define/prefer/tool-toggle）；`ctx.plugins.reloadDisk()` 运行时重扫（jsplugin.go:3111） |
| 生命周期实现 | `Reload`/`Unload`/`Undefine`/`UndefinePermanent`（plugin.go:1017-1168）——卸载完整回收（工具/片段/监听/命令/effects/提示词资产） |
| 多实例与测试 | `WEB_PORT` 多实例并行（已实测）；Go 专项测试范式（plugin_e2e/diskplugin_jsnative/ext_routes…）+ 沙箱 `harness` 预检 + cordis define 预检 |

**缺口（第一步要补的六块地基）**：

| # | 缺口 | 设计（v2 定稿） |
|---|---|---|
| 1 | **请求检查器（带放行/拒绝的中间件）** | 宿主在 ExtRouteMiddleware 外层建"检查器链"；插件经 `ctx.pipeline.register({name, order, match, handler})` 注册；handler(req) 返回 `{action:'next'|'allow'+identity|'deny', status?, body?}`；放行后进入现有路由层 |
| 2 | **身份传播（插件→Go 上下文）** | 检查器 `allow+setIdentity` → 宿主 `WithIdentity(req.Context())` → 内核 handler/隔离路由用 `IdentityFrom(ctx)` 读取；同时身份快照放进插件可见的 req 对象（`req.identity`），下游插件可读 |
| 3 | **页面级 UI 挂载点** | 壳增加"阶段"概念（boot → 未登录=登录阶段，渲染全屏登录页）；页面插件 `ui.registerPage({id, stage, render})`；内置最小回退页（卸载登录页插件不锁死） |
| 4 | **磁盘包热装载/卸载** | 装载器函数化（复用启动装载逻辑）+ 管理 API：`/api/admin/plugins`（list/load/unload/reload）；可选目录监听自动同步 |
| 5 | **配置变更实时通知** | `ctx.getSettings()` 实时读取（实施时校验）；补 `settings:changed` 事件（插件订阅重建内部状态） |
| 6 | **组合装配** | 装配器收集"已装载且启用"的检查器/页面（按声明 order 排序）；"配置动态组合" v1 语义 = **插件启停 + 各插件参数 + 声明式顺序**；站点级覆盖配置为增强项 |

**运行期优化缺口（2026-09-17 代码级核查新增；G1 并入 M1.0 调试基建，G2-G5 归第二步 M2.2/M2.3）**：

| # | 缺口 | 现状证据 | 补法 |
|---|---|---|---|
| G1 | 无 HTTP/目录级的"磁盘重扫"入口 | `reloadDisk` 仅在插件 ctx（jsplugin.go:3111） | 加 `POST /api/plugins/action {action:"rescan"}` |
| G2 | 全量重扫会重装全部插件 | `applyGlobalPlugin` 对同名"先卸再装"（toolset.go:698） | 增量重扫：比对目录 mtime/新增，只重装变更包 |
| G3 | 单插件源码热更不完整 | `Reload` 重放内存 def、不重读磁盘（plugin.go:1033） | start 前重读磁盘包（随 G2 增量重扫自然解决） |
| G4 | "停用（stop）"不跨重启 | 重启 `LoadGlobalPlugins` 全量复活（plugin.go:1156 注释） | 停用清单持久化（`.pair/plugins-state.json`），装载器跳过 |
| G5 | 无 `settings:changed` 事件 | `getSettings` 直读内存（**读取实时已成立**），但插件缓存参数时无变更通知 | 设置保存后经 EventBus 广播 |

> 核查结论：**动态插件的"运行"已具备**（装载/卸载/启停删/重扫/诊断全链路）；缺的是"调度级"细节（G1-G5：重扫入口、增量、单插件热更、停用持久化、变更通知）——与 v2 六块地基合并，即生产形态的完整补强清单。

**设计原则**：
- **失败策略**：检查器超时/异常默认 **fail-closed（拒绝）**；非关键检查器（如审计）可声明 `failOpen: true`。
- **卸载安全**：卸载认证类插件 ≠ 平台裸奔——回退为**安全默认**（拒绝未认证请求），避免热卸载开出安全洞。
- **性能**：检查器在请求 goroutine 内经 goja 调用（VM 锁保护），内网场景可接受；带超时护栏。

### 4.2 认证插件设计（边界划分）

**宿主（主体·稳定）**：
- 身份数据服务：users/sessions 的存储与 CRUD（`<InstallDir>/.pair/users/`）
- 密码学原语：bcrypt 哈希/校验（JS 沙箱无加密库，必须在 Go 侧）
- 身份上下文：`WithIdentity/IdentityFrom`、隔离路由消费

**插件（可变）**：
- 认证流程编排：login/logout/me API 端点（`ctx.webServer.register`）
- 会话策略：token 生成、cookie 设置、有效期参数（设置项）
- 请求校验器：`ctx.pipeline.register` 的认证检查器（读 cookie → `ctx.auth.resolveSession(token)` → allow+identity）

**为什么这样分**：用户主数据要被权限/隔离主干引用（会话归属、空间路由、角色），是"主干资源"而非插件私有物；插件是"认证交互与策略层"——换认证方式（密码/免登/未来扫码）不动数据模型与主干。

**第一步（v1 简单可用版）**：上述形态直接落地（JS 插件、启动装载），提供登录/登出/会话/最小登录页——平台可内网上线。
**第二步（完整化）**：参数面板（会话时长/白名单/限速）、可热替换、无返工。

### 4.3 中间件插件设计

**形态**：每个中间件 = 一个检查器插件（可独立启停）：
- 认证校验（与认证插件同族，第一步随认证提供）
- 登录限速（失败计数、429）
- 维护模式（开关参数 + 提示页）
- 审计记录（可选，failOpen）
- 未来：IP 白名单、二次确认等

**组合**：装配器按 `order` 排序收集；插件启停、参数修改 → 链重建 → 下一请求生效。

### 4.4 前端页插件设计

| 页 | 阶段 | 说明 |
|---|---|---|
| 登录页 | login（未认证） | 全屏；可替换（换风格/加公告）；内置最小回退 |
| 用户管理页 | admin（已认证） | 建号/改角色/重置密码/分配微信 |
| 角色适配 | 已认证 | 壳按角色裁剪入口（软裁剪；硬约束在后端） |

- 壳改造：boot 时先查 `/api/me` → 401 进登录阶段（只加载页面插件，不装载业务区域）；登录成功重新 boot。
- 401 全局拦截：统一请求封装层（前端 166 个 API 调用面集中处理）。

### 4.5 动态调度机制（第二步核心）

```
插件管理操作（管理界面/API/目录）：
  装载：扫描包 → 校验 → 运行 → 收集贡献物（检查器/页面/路由/工具）→ 重建装配
  卸载：停止 → 撤销注册（dispose 链）→ 链重建 → 安全回退（关键插件→安全默认）
  改参：设置项写入 → 通知（settings:changed）→ 插件重建内部状态
前端插件变更：文件覆盖 + 浏览器刷新即生效（前端资源磁盘优先）
```

> 现状核查补充：运行时全量重扫（`ctx.plugins.reloadDisk()`）与单插件启停删（`/api/plugins/action`）**现已可用**；HTTP 重扫入口 / 增量重扫 / 单插件源码热更 / 停用持久化 / 变更事件为待补项（G1-G5，见 4.1）。

## 五、数据设计

### 5.1 用户存储（宿主所有）

`<InstallDir>/.pair/users/users.json`：
```jsonc
{ "version": 1, "users": [
  { "id": "u-0001", "login": "admin", "name": "管理员", "role": "admin",
    "passHash": "$2a$10$...",        // 空=仅微信账号（禁 PC 登录）
    "spaceRoot": "D:/PairCodeData",  // 管理员=现有工作区（存量继承）
    "wechatAccountId": "", "disabled": false, "createdAt": "..." }
] }
```
会话表 `<InstallDir>/.pair/users/sessions.json`：`{token, userId, createdAt, expiresAt, lastSeenAt}`（7 天滑动；token=随机 64 hex）。

### 5.2 角色 → 能力面

| 角色 | 工具集 | 说明 | 空间根 |
|---|---|---|---|
| admin | 「全功能」 | 全部工具 + 全部管理界面/API | 现有工作区 |
| dev | 「全栈开发」 | 终端/文件/Git/代码图谱全套 | `<InstallDir>/spaces/<login>/` |
| office | 「办公」 | 文档工具 + 基础文件；无终端/代码 | 同上 |
| chat | 「聊天」（新建预设） | 纯对话 + 记忆/知识库 | 同上 |

### 5.3 隔离与共享数据

- 会话 meta：加 `userId` 字段；会话物理存储随空间根落盘（双保险）。
- 记忆：随空间根落盘（天然按用户）；共享：`<InstallDir>/.pair/memory-shares.json`（条目级 `sharedWith` 白名单）。
- 当前工作区状态：`<InstallDir>/.pair/users/<id>-state.json`（替代全局单例语义）。

### 5.4 桥绑定

accounts.json 账号加 `ownerUserId`（空=仅 admin 可用）；一人最多绑一个账号（校验）。

## 六、后端设计

### 6.1 第一步·主体改造（工作项）

## 八、开发调试环境与布署流程（2026-09-17 新增）

### 8.1 目标与隔离设计

**需求**：宿主（Go 项目）与插件（本项目插件）的开发、测试都在**独立实例**上进行；**测试通过才布署生产**；全程不触碰生产实例。

**隔离原理（已核查）**：
- `InstallDir()`：取 exe 所在目录；`bin/` 子目录自动回退上级；**路径含 `\temp\` 时回退 `os.Getwd()`**（cwd 即数据根）——internal/core/settings.go:94；
- `ConfigDir()` 同规则（settings.json 独立）；
- `WEB_PORT` 环境变量覆盖端口，端口占用即启动失败（不会静默抢占）。

**目录布局**：

```
D:/PairCodeData/
├── 开发源码/paircode-master/            ← 生产实例（9090；exe 在仓库根；.pair/plugins = 生产插件）
└── temp/host-dev/                       ← 测试实例（与生产零共享）
    ├── pair-dev.exe                     ← 测试构建（构建脚本产出并落地此处）
    ├── .pair/plugins/                   ← 待测插件装载处（测试实例专属）
    ├── config/                          ← 测试配置（独立 settings.json，不复制生产）
    └── ws/                              ← 可选：测试工作区（对话级用例用）
```

**启动姿势**：`cd temp/host-dev && WEB_PORT=9191 ./pair-dev.exe`
→ InstallDir=Getwd()=temp/host-dev（temp 特判命中）→ `.pair/` 与 `config/` 全隔离。
⚠️ 启动脚本必须 `cd` 到位——否则 InstallDir 会落到别的 cwd。

### 8.2 用例速查

| 场景 | 做法 |
|---|---|
| 宿主开发测试 | `go build ./...` + `go test` → exe 复制 temp/host-dev/ → 9191 启动 → 冒烟（health/plugins/日志 FATAL 检查） |
| 插件开发测试 | 插件包放 `temp/host-dev/.pair/plugins/<id>/` → 重扫（M1.0 rescan 端点 / 重启）→ 断言（装载 running + 行为 + 无错误） |
| 内存态快速迭代 | AI 会话 `cordis(op=define/run/stop)`——预检+装载，免磁盘、免重启 |
| UI 走查 | 浏览器 http://localhost:9191（如认证已启用则先登录） |

### 8.3 测试准入清单（插件）

1. 装载状态 `running`（无 rejected/failed；waiting 须为预期且能被依赖激活）；
2. 贡献物行为断言通过：HTTP 路由探测 / 工具调用 / 检查器放行与拒绝 / UI 渲染（client 半）；
3. 无宿主级错误：FATAL/panic=0；插件 console 无 unexpected error；
4. 卸载干净：stop 后路由/工具/检查器消失，无悬挂注册；
5. 重启一致性：测试实例重启后行为一致（防"内存态才对"）；
6. 回归：既有插件/工具面不受影响（遍历 /api/plugins 全量状态）。

### 8.4 布署流程（测试通过 → 生产）

```
1. 测试实例全项通过（8.3 清单）
2. 备份：生产 .pair/plugins/<id>/ → temp/deploy-backup/<时间戳>/
3. 投递：测试通过包 → 生产 .pair/plugins/<id>/
4. 生效：生产 rescan（M1.0 端点，热生效；G2 增量重扫补齐后无打扰）
        或 重启生产实例（rescan 未就绪时的退路）
5. 生产验证：/api/plugins 确认 running + 行为冒烟 + 日志无错
6. 回滚：备份还原 + rescan/重启；或临时 stop 该插件
```

**边界**：调试环境与"测试→布署"控制在本机（与生产同机的双实例）；将来生产迁至服务器时，测试实例同法隔离到服务器旁，布署加"构建产物同步"步骤。

### 8.5 脚本落点（建议 `scripts/plugin-dev/`）

| 脚本 | 职责 |
|---|---|
| `build-host.mjs` | 编译宿主（`CGO_ENABLED=1 go build -o pair-dev.exe ./cmd/companion`）→ 复制到 temp/host-dev/ |
| `host.mjs start\|stop\|status` | 测试实例启动（9191）/探活/终止；日志落 temp/host-dev/logs/ |
| `smoke.mjs [--port N]` | 冒烟断言（health/plugins/自定义用例；供测试与生产两用） |
| `deploy.mjs <plugin>` | 备份→投递→rescan→验证（生产侧，二次确认） |

> 脚本实现归 M1.0；冒烟用例随平台演进增补（认证/隔离越权用例从 M1.3 起进入清单）。
